# Predictive Thermal Monitor

A live dashboard that polls a machine's CPU and RAM usage in real time and uses a trained regression model to predict CPU load ~10 seconds ahead — surfacing a live "NORMAL" / "WARNING" status alongside the raw readings.

## What it does

- Logs live system telemetry (`psutil`) to a CSV over a fixed collection window
- Trains a regression model on that data to predict near-future CPU load from current stats + short-term trend
- Serves live predictions through a Flask API
- Displays current CPU, predicted CPU, and status on a live-updating dashboard with a rolling chart (Chart.js)

## Tech stack

- **Python** — `psutil`, `pandas`, `scikit-learn`, `joblib`, `Flask`
- **Frontend** — vanilla HTML/CSS/JS, Chart.js for the live graph

## How it works

1. **`logger.py`** polls `psutil` roughly once per second for a set duration (default 15 min) and logs CPU%, RAM%, and disk read/write byte counters to `data/telemetry.csv`.

2. **`train_model.py`** loads that CSV and builds features:
   - `cpu_percent`, `ram_percent` — instantaneous readings
   - `cpu_rolling_avg` — mean of the last 5 readings
   - `cpu_trend` — change from the previous reading (`.diff()`)
   
   The target is `cpu_percent` shifted 10 rows into the future (~10 seconds ahead, given ~1 row/sec logging). The model is trained with an 75/25 train/test split and evaluated with MAE/MSE on held-out data, then saved with `joblib`.

3. **`app.py`** loads the trained model at startup, and on each request to `/api/telemetry`:
   - Reads a live `psutil` snapshot
   - Maintains an in-memory buffer of the last 5 CPU readings (server-side, across requests) to compute the same rolling average/trend features used in training
   - Builds a feature row matching the training column names/order and calls `model.predict()`
   - Returns current CPU, predicted CPU, and a status flag as JSON

4. **The frontend** polls `/api/telemetry` every 3 seconds, updates the live stat boxes and status color, and pushes new points onto a rolling Chart.js line graph (last 20 readings, ~1 minute of history).

## Model performance

| Approach | MAE | Notes |
|---|---|---|
| Linear Regression, raw features | 14.52 | Baseline — instantaneous CPU/RAM only |
| Random Forest, raw features | 14.61 | No improvement over linear — confirmed the bottleneck was feature signal, not model complexity |
| Linear Regression + rolling avg/trend | 13.56 | Modest improvement from adding short-term trend information |
| Linear Regression + rolling avg/trend (new session) | **7.05** | Final model — lower MAE reflects a less volatile CPU session (std ~11 vs. ~23), not a feature change |

**Naive baseline check:** predicting the mean every time would produce an average error roughly equal to the standard deviation of `cpu_percent` (~11–23 across sessions), so the model meaningfully outperforms a "just guess the average" approach.

### Experiment: disk I/O features

Tested adding disk read/write byte deltas (`.diff()` of cumulative `psutil.disk_io_counters()`) as additional features. In a controlled comparison on the same dataset (same data, same split, only the feature set changed), this **did not improve** predictions — MAE 7.05 without vs. 7.24 with — and was excluded from the final model. Worth revisiting with a training session that includes heavier, sustained disk activity.

## Known limitations

- Predictions on individual readings can deviate from actual CPU load by 10+ percentage points, consistent with the model's measured MAE, this reflects the inherent volatility of general-purpose CPU load over a 10-second horizon, not a bug.

- Trained on a single ~15-minute session on one machine; a longer, more varied dataset (multiple sessions, different workloads, different times of day) would likely generalize better.

- `LinearRegression` was chosen after comparing against `RandomForestRegressor`, which performed no better, suggesting the current feature set, not model choice, is the main limiting factor.

## Possible extensions

- Longer/more diverse training data (multiple sessions, varied workloads)
- Additional features: per-core CPU breakdown, running process count, time-of-day
- Real hardware sensor data via IPMI/Redfish on BMC-enabled server hardware (e.g. Supermicro), in place of software-only `psutil` metrics, for genuine thermal/server-health monitoring
